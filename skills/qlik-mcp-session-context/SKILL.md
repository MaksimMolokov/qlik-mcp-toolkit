# qlik-mcp-session-context

Сохраняет провалидированные строки предыдущего ответа в рамках ТЕКУЩЕЙ
беседы, чтобы уточняющий вопрос не отправлял в Qlik новый неограниченный
запрос. Пример: «топ-10 клиентов по обороту» → «покажи, кто из НИХ принёс
убыток» → «раздели их по видам спорта» — на шагах 2 и 3 популяция обязана
остаться теми же 10, что вернул шаг 1.

## ⚠️ Изоляция между беседами — по возрасту записи, не по `session_key`

`session_key` в схеме есть, но НИКТО его реально не передаёт — везде просто
`session_store.load()` без аргументов, значит он всегда `None` и себя не
изолирует. Изоляция держится на возрасте файла: `load()` сама сбрасывает
хранилище, если последняя запись (`updated_at`) старше 2 часов
(`DEFAULT_STALE_AFTER_SECONDS`) — считает это уже другой беседой. Не
подставляй свой `stale_after_seconds`, если не пишешь тест. Живой прогон
2026-08-13 (`<app_name>`, топ-10 → follow-up без нового
Qlik-вызова → искусственно состаренная запись → сброс) — все три сценария
подтверждены, детали в `references/schema.md`.

## Перед КАЖДЫМ обращением к Qlik

1. `session_store.load()`, найди, к какому сохранённому результату относится
   «эти/те/из списка/предыдущие» (`active_result_key`).
2. Проверь: можно ли ответить локальной операцией над `active_rows()`
   (фильтр/сортировка/проекция/сравнение/сумма/мин/макс/счёт) —
   `derive_rows()`. Если да — считай локально, в MCP не ходи.
3. Если нужного поля в сохранённых строках нет (новая метрика для той же
   популяции — как «убыток» в примере выше) — сделай ОДИН новый узкий запрос,
   ограниченный ТОЧНО тем же списком сущностей: не переспрашивай метрику по
   всей базе заново (другая популяция), а построй Set Analysis
   (`hypercube_builder.set_analysis_clause` из `qlik-mcp-data-access`) по
   зафиксированному списку ID из шага 1, с теми же dimensions.
4. После ответа — `check_population_bound(store, new_row_count)`. Непустой
   список проблем = фильтр не применился, ответ пользователю не отдавать,
   разобраться и повторить.
5. Сразу сохрани результат через `upsert_query()`: `app_id`, метрика/период/
   фильтры/dimensions, полный `rows`, `grand_total`, `validation_status`,
   `reload_fingerprint`, `tool_call_seconds`. Только `validated` строки могут
   быть источником следующего follow-up.

Никогда не расширяй «эти клиенты»/«из них» обратно на всю базу. Если все
строки в кэше положительны, а пользователь спрашивает про отрицательные —
ответ «таких нет среди этих десяти» БЕЗ нового запроса к Qlik.

Формат хранилища — [schema.md](references/schema.md). Никогда не сохраняй
JWT, заголовки авторизации, сырые чувствительные логи.

## Что скилл НЕ делает

- Не вызывает `mcp__qlik__*` сам — только агент. Этот скилл только решает,
  нужен ли новый вызов вообще, и если да — с каким сужением.
- Не заменяет `qlik-mcp-data-access` (валидация hypercube) и
  `qlik-mcp-analysis` (семантика/паспорт) — работает вместе с ними.
- Не хранит данные дольше одной беседы/задачи — постоянный кросс-сессионный
  кэш семантики приложения (не строк результата) — зона `app_cache.py` из
  `qlik-mcp-data-access`.
