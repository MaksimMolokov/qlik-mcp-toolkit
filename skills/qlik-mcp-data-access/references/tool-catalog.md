## ✅ Апгрейд до 2.0.0 — схема и поведение подтверждены live 13.08.2026

`uv tool upgrade qlik-sense-mcp-server` (12.08, после `Stop-Process -Force`

напрямую у MCP-клиента. **14 инструментов в JWT-режиме** (не 12, не 13 —
апстрим добавил и `search_app`, и `engine_query` с 1.7.2).

**Главное изменение — новый инструмент `engine_query`**, проверен реальным
batch-вызовом на `llm_model_top50_clients` (2 независимых запроса за один
round-trip): `group_by` + `metrics` (`{field, agg}`) + `filters`
(период/диапазон/значение, сервер репортит реально покрытый период через
`period_check`/`filters_applied`) + `sort_by`/`limit`, без ручных Set
Analysis выражений — для типовых group-by-агрегатов короче, чем собирать
`engine_create_hypercube` вручную; для `Aggr()`/кастомного Set Analysis
`engine_create_hypercube` остаётся нужен.

**Готча, подтверждённая живьём, которой нет в CHANGELOG апстрима**:
`group_by`/`metrics[].field`/`filters[].field` в `engine_query` — это НЕ
имя поля напрямую, а Qlik-выражение, которое сервер парсит как есть.
Многословное имя без `[Квадратных скобок]` падает с `error_category:
invalid_expression` / `Garbage after expression`; с `[Вид спорта]` тот же
запрос проходит. **УСТАРЕЛО (см. раздел "2.0.0 → 2.0.2" в начале файла):**
на 2.0.2 `engine_create_hypercube.dimensions[].field` ТО ЖЕ САМОЕ
ограничение ИМЕЕТ — там тоже выражение, скобки нужны. Всегда оборачивай
через `hypercube_builder.quote_field()` при сборке
`engine_query`.

**Новый `{filter}`-маркер в `engine_create_hypercube`** — тоже подтверждён
живьём: мера вида `Sum({filter} [Оборот по позиции])` + top-level
`filters: [{"field": "[Вид спорта]", "values": [...]}]` — сервер сам
подставляет Set Analysis (`{<[Вид спорта]={'...','...'}>}`) и возвращает
`filters_applied` с уже разрешённым выражением. Полезно, когда фильтр
одинаковый для всех мер запроса и не хочется вручную формировать
`set_analysis_clause()`.

Другое (из CHANGELOG/README апстрима, отдельно прицельно не
перепроверялось в этом прогоне): unknown field names теперь **отклоняются**
(не просто warning, как в 1.9.0) — проверить, не ломает ли это уже
написанные выражения, которые полагались на тихий 0 вместо ошибки; даты в
результатах — в формате Qlik, не serial-число (раньше приходилось
конвертировать вручную, см. `answers_v3_190/001...md`); валидация
выражений перенесена в Engine (заявлено ~75мс→~4мс); WebSocket CSRF-token
теперь в URL; 10 env-переменных убрано, осталось 15 `QLIK_*`. Полная
история и живой протокол — `Work\.claude\skills\mcp-qlik\SKILL.md`.

### Ключевые изменения 1.7.2 → 1.9.0 (по CHANGELOG, пока не live-подтверждено)

  фиксился) — автор переписал health-check: вместо `ping`/`pong` (который в

  Заявлено ускорение с ~63с до ~0.005с на повторных вызовах. **Правило "до

- `get_app_field_statistics` — null-статистика теперь считается через

## Как определить, какая схема `engine_create_hypercube` реально активна

Перед первым вызовом в новой сессии — либо посмотри реальную JSON Schema
инструмента, которую тебе показал MCP-клиент (если она содержит `sort_by`/
`limit`/`exclude_null_dimensions` НА ВЕРХНЕМ уровне — сервер уже 1.6.0+,
можно использовать modern-путь ниже), либо просто отправь первый реальный
запрос legacy-схемой (она гарантированно работает на ЛЮБОЙ версии сервера,
включая 1.7.2 — параметры не были удалены, только добавлены новые
альтернативные) и не усложняй, если результат устраивает.

## Legacy-схема (fallback, работает на любой версии сервера включая текущую 1.7.2)

Не «актуальная схема» — это запасной путь. Сейчас сервер обновлён до
1.7.2 и modern-схема (следующий раздел) подтверждена живьём и должна
использоваться как ОСНОВНАЯ. Legacy оставлена как fallback на случай
отката/переустановки сервера без пина версии, и для адресной выборки по
списку известных ID (`build_id_list_sort_expression`), где приём
`qSortByExpression` всё ещё нужен даже на modern.

```json
{
  "app_id": "string, обязателен",
  "dimensions": [
    {"field": "ИмяПоля", "sort_by": {"qSortByExpression": -1, "qExpression": "Sum(...)"}}
  ],
  "measures": [
    {"expression": "Sum(...)", "label": "Метка"}
  ],
  "max_rows": 10
}
```

Топ-N/ranking — через `max_rows` + `qSortByExpression` внутри объекта
dimension (`hypercube_builder.build_dimension(field, sort_by_expression=...)`
или `build_id_list_sort_expression()` для адресной выборки по списку ID).

## Modern-схема (v1.6.0+) — ✅ подтверждена live 07.08.2026 на сервере 1.7.2

Прогнан живой запрос на `llm_model_top50_clients` (top-10 по `Оборот` desc):
`sort_by`/`sort_order`/`limit` на верхнем уровне отработали корректно,
результат (клиенты + значения) идентичен ранее известному legacy-результату
на той же популяции. Использовать как ОСНОВНУЮ схему теперь можно.

Формат по README github.com/bintocher/qlik-sense-mcp (актуален на 31.07.2026, v1.7.2):

```json
{
  "app_id": "<guid>",
  "dimensions": [{"field": "clientid"}],
  "measures": [{"expression": "Sum(ggr)", "label": "GGR"}],
  "sort_by": "GGR",
  "sort_order": "desc",
  "limit": 10,
  "exclude_null_dimensions": true,
  "include_raw_layout": false
}
```

- `sort_by` (string) — метка меры, выражение меры ИЛИ имя измерения (не объект,
  не `qSortByExpression` внутри dimension).
- `sort_order` — `"desc"`/`"asc"`.
- `limit` — заменяет `max_rows` по смыслу (отклоняется, если > 5000).
- `exclude_null_dimensions` — по умолчанию `true`, исключает группу `"-"` с
  пустыми значениями измерения (сейчас это приходится делать вручную,
  фильтруя `qIsNull`/`"-"` на стороне агента — видно во многих ответах
  стейдж-циклов, например 001/016/019).
- `include_raw_layout` — `true` вернёт полный layout Qlik (обычно не нужно).
- Жёсткий лимит ячеек не изменился: `columns * max_rows/limit > 9900` —
  запрос отклоняется.

**Когда сервер обновится до 1.6.0+ — modern-путь короче (не нужен
`qSortByExpression`-трюк для простого top-N по значению самой меры), но для
адресной выборки по списку известных ID (`build_id_list_sort_expression`)
legacy-приём с `Count({<[Field]={ids}>}...)` в `qSortByExpression` всё равно
может понадобиться, т.к. `sort_by` в modern-схеме сортирует по значению
меры/измерения, а не по «искусственному» флагу принадлежности списку —
уточнить живым тестом после апгрейда.**

## Реконнект / `QLIK_WS_TIMEOUT` — важное расхождение с документацией GitHub (история версий ≤1.7.2)

README текущей ветки заявляет: «Dropped connections are reopened
transparently» — сервер сам переоткрывает WebSocket при разрыве, в рамках
той же клиентской сессии. **Живое поведение версии 1.5.1 этому НЕ
соответствует** — за оба прогона (04-05.08 и 07.08) сбой `CreateSessionObject`
(WS-таймаут ~180с, ровно значение `QLIK_WS_TIMEOUT` по умолчанию) происходил
систематически и ТРЕБОВАЛ ручного повтора со стороны агента; сервер сам
восстановиться не смог ни разу.

**❌ Опровергнуто на 1.7.2 (07.08.2026, после апгрейда).** Гипотеза «апгрейд
устранит/уменьшит баг» НЕ подтвердилась: из 3 «холодных» вызовов к Engine
в свежей сессии (после перезапуска Claude Code) 2 упали на первой попытке
(`get_app_details` → `GetTablesAndKeys`, 364с; `engine_create_hypercube` →
`CreateSessionObject`, 232с) — ~67% первых попыток, не лучше исходных
>50% на 1.5.1. Хуже того: второй из этих вызовов упал ЕЩЁ РАЗ на первом
ретрае (183с) и потребовал ВТОРОЙ ретрай, чтобы пройти (2.9с) — раньше
одного повтора почти всегда хватало. **Вывод: правило "повтори до двух раз"
остаётся обязательным и на 1.7.2, `QLIK_WS_TIMEOUT`-баг не исправлен, заявление
README про transparent reconnect не подтверждается практикой.**
