# Проверка результата перед ответом

- **Кэш паспорта сохранён.** Если это первое обращение к данному `app_id` в
  этой беседе И контракт не был взят из уже существующего кэша (`shape
  cache_hit=false` на шаге 3 workflow) — `app_cache.upsert_contract()`
  ОБЯЗАН быть вызван до этого пункта, не после ответа пользователю. Живой
  факт (07.08.2026, стейдж 2): за весь прогон этот вызов не сработал ни
  разу, несмотря на прямое требование в `SKILL.md` шаг 12 — то есть
  «пропиши правило» само по себе не работает, проверяй фактическое наличие
  записи в `app-cache.json` для этого `app_id` перед тем, как отдать ответ.
  Пропуск этого шага не блокирует текущий ответ по существу, но означает,
  что следующая беседа снова заплатит полным чтением `get_app_script` —
  то есть каждый пропуск прямо снижает будущую скорость.
- **Нули/пусто.** GGR/убыток = 0 неожиданно — проверь минимальным
  `Sum(field)` без фильтров: поле может быть с обратным знаком или не тем
  полем (несколько полей могут значить «доход» в обиходе).
- **NaN.** `qNum: "NaN"` у текстового измерения — норма, бери `qText`. У
  measure — обычно NULL/нет данных, не арифметика вслепую.
- **Усечение.** Сверь `total_rows` vs `returned_rows` и текст
  `truncation_warning` — если пользователю нужен полный список, а не top-N,
  подними `max_rows` осознанно или сообщи об усечении явно.
- **Grand total vs строки.** Если использовалась `exclude_null_dimensions`-
  подобная фильтрация (у текущей схемы её нет как параметра — фильтруй NULL
  локально), сумма видимых строк может быть меньше `qGrandTotalRow`.
- **Sanity-числа из Description.** Если во вкладке `Description` есть
  готовое проверочное число по похожему фильтру — сверь с ним. Расхождение
  сильно больше разумного дрейфа данных (единицы процентов за несколько
  дней) — повод перепроверить выражение, а не выдавать ответ с уверенностью.
- **Population-lock (уточняющие вопросы).** Число строк в ответе на follow-up
  не может превышать размер зафиксированной популяции — см.
  `qlik-mcp-session-context/scripts/session_store.py::check_population_bound`.
- **Знак прибыли/убытка.** `Win/Loss`/`Profit`/`GGR` — знак показывает
  направление; если выглядит перевёрнутым, проверь `Sum(field)` без фильтров.
- **Count() vs Count(DISTINCT).** Перед подсчётом количества (не суммы)
  через `Count()` сначала проверь по Description/структуре таблицы, не
  может ли одна бизнес-сущность занимать несколько строк источника
  (составные/многострочные записи). Если может — используй
  `Count(DISTINCT <ключевое поле сущности>)`, никогда голый `Count()`
  вслепую.
- **Composite-метрика не из паспорта.** Если запрошена метрика, которой нет
  буквально (с формулой) в документированной семантике приложения — не
  подбирай формулу молча по смыслу названия и не останавливайся на «такого
  нет». Следуй протоколу из `SKILL.md` → «Показатель не подтверждён в
  текущем приложении» (зафиксировать/поискать в других приложениях/сверить
  ключ соединения/назвать источник в ответе/честно сообщить, если не
  нашлось нигде).
- **Несколько полей с похожим смыслом (расширено 07.08.2026).** Не только
  составные формулы — в модели могут существовать НЕСКОЛЬКО ГОТОВЫХ полей
  под один и тот же обиходный вопрос пользователя, дающих разные числа.
  Живые примеры из стейдж-2: `Payments.PaymentAmount` vs
  `lifetime.IncomingPaymentsAmount` разошлись на ~14% на одном клиенте
  (какая сумма депозитов «правильная»); «Программа лояльности (текущая)»
  vs «Макс статус за 3 года» дали 45,1% и 51,6% доли Platinum на одной и
  той же выборке (какой VIP-статус «текущий»). Перед ответом на вопрос типа
  «сколько он внёс/вывел» или «какой у него статус» — проверь, нет ли в
  модели второго кандидата на то же самое поле; если есть, **явно назови,
  из какого именно поля взят ответ**, и предупреди, что альтернативное поле
  может дать другое число, а не выбирай молча.

Не выдавай результат, пока не прошёл применимые проверки выше.
