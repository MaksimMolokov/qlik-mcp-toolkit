# Последовательности вызовов

## Шаг 0 — ДО первого вызова к Qlik вообще

Если вопрос не называет явно ни метрику, ни период, ни (при неоднозначности
из нескольких приложений) само приложение — задай уточняющий вопрос
пользователю и ОСТАНОВИСЬ, не делай широкий запрос «на всякий случай» (см.
`SKILL.md`, шаг 1a). Это главный рычаг скорости во всей цепочке: один лишний
широкий вызов стоит дороже, чем любая оптимизация конкретного запроса.

## Первый вопрос по приложению, которого нет в кэше

1. `get_apps(name=<фрагмент>)` — найди `app_id`, не угадывай GUID.
2. Проверь `app_cache.get_cached_contract(app_id, reload_fingerprint)`
   (`qlik-mcp-data-access`) — это и есть сверка `reload_dttm`/
   `modified_dttm` (отпечаток встроен в саму функцию, отдельно вручную
   сверять дату не нужно, но пропустить сам вызов нельзя: без него кэш
   молча остаётся стухшим). Если попадание — пропусти шаги 3-5, сразу к 6.
3. `get_app_details(app_id)` — метаданные, поля, cardinality; заодно даёт
   `modified_dttm`/`reload_dttm` для `reload_fingerprint`.
4. `get_app_script(app_id)` — прочитай ПОЛНОСТЬЮ, найди блок `Description`.
5. Собери контракт расчёта (`semantic-layer.md`) и сразу
   `app_cache.upsert_contract()`, чтобы следующая беседа по этому app_id не
   платила снова за шаги 3-4.
6. `engine_get_field_range`/`get_app_field` — если нужно узнать границы/формат
   значения перед фильтром.
7. `engine_create_hypercube` (через `hypercube_builder`), measures-only
   сначала, потом добавляй dimensions.
8. Провалидируй ответ (`validation.md`), сохрани в session-context
   (`upsert_query`).

## Вопрос по приложению, которое уже открывали в этой беседе

Проверь `qlik-mcp-session-context` ПЕРЕД любым новым вызовом — возможно,
ответ считается локально без обращения к Qlik вообще (см. SKILL.md того
скилла).

## Эталон — существующий график/лист

Если нужно воспроизвести то, что уже показано на дашборде: `get_app_sheets`
→ `get_app_sheet_objects` → `get_app_object`, прочитай Description/expression/
dimension/measure/layout объекта — это авторитетнее, чем собственная
реконструкция формулы.

## На таймаут/ошибку

1. Если `error_category: connection_error` и `failed_step` в
   {`CreateSessionObject`, `OpenDoc`, null} — повтори тот же вызов до ДВУХ
   раз с теми же аргументами, прежде чем сообщать о проблеме (см.
   `qlik-mcp-data-access/references/tool-catalog.md`). Известное поведение
   самого Engine (держит одно WS-соединение, которое протухает и не
   переподключается с первой попытки) — не специфика конкретного
   приложения. Одного повтора на практике достаточно не всегда — стейдж-2
   регрессия (07.08.2026) поймала минимум два случая сбоя СРАЗУ ПОСЛЕ
   успешного тёплого вызова к тому же приложению, не только «первый после
   паузы». После ДВУХ неудач — честно сообщи о проблеме, не выдумывай число.
2. **Отдельный класс сбоя** (не путать с п.1): `error_type: QlikConnectionError`,
   текст ошибки содержит `JwtBootstrapError`/`csrftoken request failed` —
   таймаут самого JWT-бутстрапа, не Engine WS. Диагностика —
   `hypercube_builder.is_jwt_bootstrap_error()`. Та же тактика (повтор), но
   упомяни отдельно в отчёте, если встретится — впервые пойман 07.08.2026.
3. Любая другая ошибка — прочитай `truncation_warning`/`hint` в ответе
   сервера, поправь запрос (уже, meaner measures, ниже cardinality) и
   попробуй снова. Не пиши «MCP не работает» после первой неудачи.
