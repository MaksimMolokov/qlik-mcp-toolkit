# qlik-mcp-analysis

Использует `qlik-mcp-data-access` (валидация/сборка hypercube, постоянный
кэш семантики) и `qlik-mcp-session-context` (population-lock для уточнений) —
не дублирует их логику.

## Обязательный семантический workflow

Полное чтение скрипта/листов/объектов — десятки тысяч символов контекста за
раз. Не повторяй это на каждый вопрос и на каждую новую беседу.

1. Проверь `qlik-mcp-session-context` — возможно, вопрос про уже открытую
   популяцию и отвечается локально без обращения к Qlik.
1a. **Вопрос без метрики/периода/приложения — уточни ДО вызова MCP.**
    (Пункт из плана `06. Анализ текущего состояния и план развития MCP.md`,
    07.08.2026: не был внесён технически до этой правки, хотя рекомендован
    05.08 — «выгрузи мне весь клик» и подобные широкие формулировки лечатся
    явным уточняющим вопросом, не ускорением сервера.) Если пользователь не
    назвал явно ни метрику, ни период, ни (при неоднозначности) приложение —
    спроси, а не угадывай самое вероятное намерение и не делай широкий
    запрос «на всякий случай».
2. Найди приложение через `get_apps`, узкий фильтр, не угадывай `app_id`.
3. Проверь постоянный кэш (`qlik-mcp-data-access\notes.md` /
   `app_cache.get_cached_contract`) по `app_id`+`reload_fingerprint`. Совпал —
   переиспользуй контракт, пропусти пп. 4-6. Не совпал/нет — выполняй их и
   обнови кэш сразу после.
4. Прочитай полное `description` приложения (`get_apps`/`get_app_details`).
5. `get_app_script` — найди блок `Description`/паспорт, вычитай целиком.
6. `get_app_details` — сверь регистр полей, таблицы, cardinality, reload-время.
7. Собери контракт расчёта (`references/semantic-layer.md`) ДО первого
   data-запроса.
8. Для нетривиальной логики — `get_app_variables`; для эталонного графика —
   `get_app_sheets` → `get_app_sheet_objects` → `get_app_object`.
9. Простое «сколько/сколько раз, по чему» — `engine_query`
   (`hypercube_builder.build_engine_query()`, v2.0.0+); `Aggr()`/кастомный
   Set Analysis/сравнение двух периодов в одной колонке — hypercube через
   `qlik-mcp-data-access/scripts/hypercube_builder.py`.
10. При `connection_error` на `CreateSessionObject`/`OpenDoc` — повтори тот
    же вызов до ДВУХ раз, прежде чем сообщать о проблеме (см.
    `references/tool-workflows.md`) — известное поведение Engine (держит
    одно WS-соединение, которое протухает и не переподключается с первой
    попытки), одного повтора на практике достаточно не всегда.
11. Провалидируй результат (`references/validation.md`).
12. Сохрани в session-context; если новый `app_id` ИЛИ впервые за эту
    беседу прочитан паспорт — ОБЯЗАТЕЛЬНО вызови
    `app_cache.upsert_contract()` с заполненным `known_traps` (любые
    найденные ловушки полей/подсчётов). Это обязательный шаг, не
    опциональный — иначе накопленное знание о приложении не переживает
    текущую беседу.
13. Не выдавай результат, пока не прошёл применимые проверки.

При конфликте описания со свежими метаданными — не выбирай молча одну
версию, явно сообщи о расхождении.

## Показатель не подтверждён в текущем приложении

Если запрошенный показатель НЕ находится verbatim в паспорте/полях/мерах/
переменных приложения, у которого сейчас открыт контракт (случай встретился
живьём 07.08.2026 — запрошенный NGR отсутствовал в обоих приложениях
скоупа `answers_v3`) — запрещены все три «лёгких» выхода: подставить похожий
по названию показатель, вывести формулу самостоятельно по общим знаниям о
домене, или просто ответить «такого показателя нет» и остановиться. Вместо
этого обязательна последовательность:

1. **Зафиксируй явно, что есть, а чего нет** — назови показатель, который
   спросили, и прямо скажи, что он не найден в разделах METRICS/GLOSSARY/
   FLAG ENCODING текущего паспорта (не в `get_app_details`/`get_app_variables`
   как отдельное поле/переменная).
2. **Поищи показатель в других доступных приложениях** — по их `description`
   (`get_apps`) и, если похоже подходит, по паспорту (`get_app_script` →
   `Description`). Не открывать весь каталог наугад — искать по смысловому
   совпадению названия/домена, как обычный шаг 2 workflow. Дёшево (кэш
   `app_cache`, уже известные приложения скоупа, `get_apps`/сверка одного
   паспорта) — ищи сразу, без запроса разрешения, это не дольше обычного
   шага 2-6 workflow. Дорого (много кандидатов, придётся читать несколько
   незнакомых `get_app_script` подряд) — спроси пользователя, продолжать ли
   поиск, вместо того чтобы молча тратить время на подряд идущие тяжёлые
   вызовы.
3. **Если нашёлся кандидат в другом приложении** — прежде чем тянуть
   значение, сверь ключ соединения между приложениями (номер клиента и
   аналогичные идентификаторы могут называться по-разному и физически не
   совпадать между приложениями — живой пример: `llm_model_top50_clients`
   ↔ `Профиль клиента (MCP)` соединяются по `[Номер клиента]`, а НЕ по
   `ClientId`, хотя оба выглядят как «идентификатор клиента»; проверено
   07.08.2026, 0 совпадений при неверном ключе). Тяни значение для ТОЙ ЖЕ
   популяции/периода, что просил пользователь — не любой ближайший период.
4. **В ответе прямо назови приложение-источник** этого конкретного
   показателя — пользователь должен видеть, что данные разных метрик в
   одном ответе могут приходить из разных приложений, а не молча считать
   всё одним источником.
5. **Если не нашёл нигде** — скажи об этом честно и перечисли, что именно
   проверил (какие приложения, по каким разделам паспорта/полям), чтобы
   пользователь мог сам решить, расширять ли поиск или считать вопрос не
   покрытым MCP-данными.

## Что скилл НЕ делает

- Не настраивает MCP-подключение (`mcp-qlik`) и не тестирует его
  (`mcp-qlik-test`).
- Не заменяет `qlik-engine`/`qlik-qrs` (cert-based, независимый инструмент).
- Не зашивает текущие бизнес-формулы сюда как вечную истину — источник
  истины живой (Description + скрипт конкретного `app_id`).
