# Семантический слой: откуда брать смысл метрик

Приоритет источников (от самого надёжного к самому слабому):

1. **`qlik-mcp-data-access\notes.md` / `app-cache.json`** — уже извлечённая и
   провалидированная выжимка для этого `app_id` с совпадающим
   `reload_fingerprint`. Если есть — используй как есть, не перечитывай скрипт.
2. **Блок `Description` во вкладке `get_app_script`** — курируемый паспорт
   (термин из вопроса → точное имя поля, обязательные модификаторы Set
   Analysis, валюта, календарные особенности, готовые sanity-числа). Ищи
   регистронезависимо варианты `Description`/`Passport`/`Паспорт`/`Info`.
   Вкладка может физически стоять после `exit script;` — это не важно для
   ЧТЕНИЯ скрипта, только для reload.
3. **`description` приложения из `get_apps`/`get_app_details`** — короткий
   текст о назначении отчёта, без карты полей. У части приложений этот
   текст пустой — тогда сразу переходи к пункту 2.
3a. **`comment`/`field_comment` в `get_app_details`/`get_app_field`**
    (подтверждено живьём на сервере 1.7.2, 07.08.2026) — точечное пояснение
    к конкретному полю/таблице из `COMMENT FIELD`/`COMMENT TABLE` скрипта.
    Дешевле паспорта (данные уже в ответе, который ты и так запросил на шаге
    6 workflow — не отдельный вызов), но это точечная подсказка про ОДНО
    поле, не бизнес-контракт целиком — не заменяет чтение блока
    `Description` (п.2) для формул/периодов/фильтров, только ускоряет
    понимание отдельных названий полей, когда паспорт их не упоминает явно.
4. **Имена/теги полей из `get_app_details`** — самый слабый источник, только
   когда пп. 1-3a ничего не дали. Никогда не угадывай смысл метрики только по
   похожему названию поля.

При конфликте между источниками — не выбирай молча один: явно сообщи о
расхождении пользователю или, если решение очевидно (например, Description
явно новее последнего reload), обоснуй выбор в ответе.

## Обязательный контракт расчёта (строй ДО первого data-запроса)

- определение показателя и авторитетная формула;
- валюта и единицы;
- точный период и логика накопительного окна;
- фильтры и измерения;
- где нужна реальная selection, а где допустим Set Analysis;
- календарь и точные (регистрозависимые) имена полей;
- golden totals / sanity-числа из Description, если есть — сверяй с ними
  финальный результат перед ответом.

## Номер клиента, а не технический ID

В любых результатах о клиентах — бизнес-номер клиента, не technical
client ID/surrogate key/GUID. Определи точное поле по QRS-description,
script-description, `get_app_details`, variables. Если подтверждённого номера
нет — явно сообщи об ограничении, не выдавай ID под видом номера.
